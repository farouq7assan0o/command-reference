# AUTHORING GUIDE - read this before adding or redoing ANY module

This is the single checklist every author (AI or human) follows when turning a module's notes
into command cards. It ties together the three sources of truth:

- **`SCHEMA.md`** - the FROZEN card contract (fields, types, policies). What a card must look like.
- **`js/vars.js`** - the canonical placeholder vocabulary. Which `<tokens>` to use.
- **`validate.js`** - the automated gate. Run it; it tells you if you're done.

If you only remember one thing: **author to the schema, then run `node validate.js` and make it PASS.**
The tool answers "is this module correct and complete?" so you never have to eyeball it or redo it.

---

## The workflow (per module)

1. **Read the ENTIRE module source** in `CPTS notes/<NN ...>/` - every `... - Commands.md` and
   `... - EXPLANATION NOTES.md`. Read every fenced code block. Do not skim.

2. **Generate one JSON card per command/technique** under `commands/cpts/<phase>/<technique>/`,
   following `SCHEMA.md` exactly. Apply the capture-everything policy - represent every command
   (as `command`, `variations`, `steps`, `examples`, or a `reference`/`attack-chain` card).

3. **Use canonical placeholders** from `js/vars.js` (see the vocabulary rules in `SCHEMA.md`).
   `<ip>` not `<target>`/`<rhost>`; `<user>` not `<username>`; `<nt_hash>` not `<ntlm_hash>`.

4. **Set the fields:**
   - `opsec`: REQUIRED - "silent" | "quiet" | "moderate" | "loud" (how detectable it is). Guide:
     silent = passive/offline (OSINT, cracking, reference); quiet = single valid request / normal
     auth / file transfer / tunnel; moderate = scans, enumeration, fuzzing; loud = exploits, mass
     brute/spray, LSASS dump, coercion, payloads, most privesc & lateral movement. The validator
     warns and --strict fails on any card missing it.
   - `mitre`: ATT&CK IDs like `["T1003.001"]` - encouraged where a TTP applies.
   - `tools`: every card should name its tool(s) so the Tool filter works.
   - `references`: >=1, following the composition rule in SCHEMA.md - (1) the tool's official
     repo/doc, (2) the HTB Academy module link `https://academy.hackthebox.com/module/details/<id>`
     (the validator warns if this is missing), (3) the CVE/vendor advisory for exploits.
   - `recommended`: the attack-chain next steps as `{"id","note?","rel?}` (rel = next |
     alternative | prereq | escalation | cleanup). Use `node suggest-chains.js --module NN` for
     candidates. Do NOT copy the target's title/description - the app looks them up live.

5. **Build**: `node build-commands.js` (regenerates `js/commands.js`).

6. **Validate**: `node validate.js` (runs automatically after `node build-commands.js` too).
   This is the gate - see the checklist below.

7. **Coverage check** (did you capture everything?): `node coverage.js --module NN`. It diffs the
   source module's command blocks against your cards and lists any source command with NO matching
   card. It scans BOTH `... - Commands.md` AND `... - EXPLANATION NOTES.md` (fenced blocks in the
   notes), so a command that lives only in the explanation notes is still flagged - each unmatched
   line is tagged `[Commands]` or `[Notes]`, and notes-only omissions are surfaced first. Review
   each: card it, or confirm it's an intentional skip (help dump / GUI walkthrough / flag-reference
   table / env setup). Setup/nav lines are auto-filtered. This is how you KNOW the whole module was
   read and nothing was silently dropped. (Fuzzy match - strong on CLI tools, weaker on PowerShell
   pipelines; treat as a review list, not proof.)

8. **Update `PROGRESS.md`**: tick the module in the checklist, update the running total, and
   append a one-line work-log entry (case -> what was done -> result).

## Where things live (orient first)

- Working directory = the `command-reference/` project folder (this repo). Run all `node` commands
  from here. `build-commands.js`, `validate.js`, `coverage.js`, `suggest-chains.js` are at the root.
- Source notes = a SIBLING folder `../CPTS notes/<NN Module Name>/`, each with a
  `<name> - Commands.md` (the commands) and a `<name> - EXPLANATION NOTES.md` (context). Note some
  filenames use `-Commands.md` (no space) - match loosely.
- Card files = `commands/cpts/<phase>/<technique>/*.json`. Shared/cross-module cards =
  `commands/_shared/` with `source: "Shared - Cross-Module Reference"`.
- `js/commands.js` is GENERATED by the build - never hand-edit it.

## Redoing an existing module (extra steps)

A "redo" re-mines a module's source and replaces its cards. In addition to the workflow above:

1. **Find the module's current cards**: `grep -rl "Module NN" commands/` (matches the `source`
   field). That's the set to replace.
2. **Read the source AND the old cards** - keep good ids where a card still applies (so
   cross-module `recommended` links don't break), improve the rest.
3. **Retire cards you're replacing** by overwriting each old file with a one-line tombstone
   `{"_ignore":true}` (deletes are blocked on the mounted drive; the build skips tombstones).
   Do NOT create a second card with the same id - dedupe by tombstoning the old file.
4. **Re-run validate** after tombstoning to catch `recommended` links from OTHER modules that
   pointed at ids you retired; repoint them.
5. Preserve ids that other modules reference (the validate broken-link check tells you which).

## The QA gate - a module is DONE when this passes

Run `node validate.js` (or `node validate.js --module NN` to scope to one module).

### MUST pass (hard errors - the site/build breaks otherwise). Target: **0**.
- Every card has all REQUIRED fields, non-empty (`id`, `name`, `command`, `description`,
  `platform`, `category`, `subcategory`, `source`, `references`).
- `platform` is linux|windows; `type` is a valid type; `opsec` is a valid level; `mitre` ids
  are well-formed.
- No duplicate `id`s. No broken `recommended` links. `references` entries have title+url.
- No empty command strings (blank command bar). Valid JSON.

### MUST pass (command lint - hardcoded literals). Target: **0**.
The `command`/`variations` are TEMPLATES - target-specific values must be `<placeholders>`
(see "THE COMMAND IS A TEMPLATE" in SCHEMA.md). The lint flags any baked-in lab literal
(IP ranges, `.htb`, htb-student/cry0l1t3). Fix each: put the placeholder in the command
(`<ip>` target / `<lhost>` your box / `<cidr>` / `<domain>` / `<user>`) and keep the concrete
value in `examples`. Only a variation that deliberately demonstrates a literal INPUT FORMAT may
carry `"lint_ignore": ["hardcoded-literal"]`. A card that fails this shows "No parameters" in the
builder - that's the symptom.

### SHOULD review (completeness table - warnings, not failures)
Each module gets a score from: has-examples, captioned-examples, has-notes, has-chains, has-tools.
- **NoEx** / **PlainEx**: prefer captioned `{label, command}` examples over plain strings.
- **NoNotes**: add a short caveat/cleanup/context note where the source has one.
- **NoChain**: fill `recommended` (attack-chain next steps). Run
  `node suggest-chains.js --module NN` to get ranked candidates, then add the good ones as
  `{"id","note","rel"}`. `validate.js` prints overall chain coverage + the weakest categories.
- **NoTools**: every card should name its tool(s).
- **Def**: defense-populated / eligible (command·payload·attack-chain) cards in the module. A
  reference/cheatsheet/script card is NOT eligible (shows `-`). This column tells you at a glance
  how much of a module's defense (🛡 Defend / 💡 Understand) content is done.
Aim to push each module's score toward 90%+. Use `--strict` to make <90% fail (for CI).

### `--strict` gates (opt-in; exit 1 on any gap, "STRICT FAIL")
`node validate.js --module NN --strict` fails the run if the module has any of:
- a completeness score <90%, or a hardcoded literal, or a card missing `opsec`, OR
- an ELIGIBLE card (command/payload/attack-chain) with NO `defense` content. This is the
  "a module can't silently ship half-done" gate - it lists exactly which cards still need the
  study/defense fields. Schema stays clean (RESULT still distinguishes hard-error FAIL from
  STRICT FAIL), but the exit code is 1 so CI/you can block on it per module.

### SHOULD review (group audit - category tree)
`validate.js` loads `js/groups.js` and flags any subcategory in a GROUPED category that isn't
assigned to a tree group (it would fall into the "Other" fallback). If you add a new subcategory
to a card in a grouped category (Enumeration, Exploitation, Active Directory, Lateral Movement,
etc.), add it to `GROUP_MAP` in `js/groups.js` - no card files change, it's a pure render map.
`--strict` fails on unmapped subcategories. Flat categories (no groups.js entry) are exempt.

### SHOULD review (placeholder audit)
Any `<token>` used 3+ times that is NOT in `js/vars.js` is flagged. For each:
- Same concept as an existing var, new spelling -> rename to the canonical token, OR add it as
  an alias in `js/vars.js`.
- A genuinely new REUSABLE engagement variable -> add a new entry in `js/vars.js` (it then
  appears in the context bar automatically).
- A true one-off local to one command -> leave it (it still gets a per-command builder field).

### Coverage (informational)
`opsec` / `mitre` coverage is printed so you can track backfill. Not required to pass.

## Pre-commit checklist (copy/paste)

```
[ ] Read the whole module source (every fenced block — no skimming)
[ ] One card per command; capture-everything (nothing dropped to an unrendered field)
[ ] Canonical placeholders only (checked against js/vars.js)
[ ] opsec set on EVERY card (required); tools[] set; mitre added where a TTP applies

REFERENCES — every card must satisfy all three:
[ ] Tool's official repo/docs/man page in references
[ ] Cert course page in references:
      OSCP -> https://www.offsec.com/courses/pen-200/
      CPTS -> https://academy.hackthebox.com/module/details/<id>
      CWES/CDSA/CRTP -> relevant course/module URL
[ ] If certifications[] has OSCP, OffSec URL is in references. If CPTS, HTB Academy URL is in references.
[ ] For exploits: CVE advisory or vulnerability write-up in references
[ ] For MITRE-tagged cards: attack.mitre.org/techniques/TXXX in references

RECOMMENDED CHAIN — every card must have:
[ ] At least ONE entry with rel="next" OR rel="prereq" (not only alternatives/escalations)
[ ] prereq links to what must be confirmed/done first (recon step, enumeration, condition)
[ ] next links to the natural follow-on after success
[ ] If this card is the chain END (root shell etc): prereq to what enabled it + escalation to what's next

MULTI-CERT — when patching an existing card to add a new cert's content:
[ ] Add new cert to certifications[] array
[ ] Add new cert's course URL to references if not present
[ ] Add to notes: "Also covered in: [Cert] [Chapter/Module]"
[ ] Do NOT change source field (records original authorship)
[ ] Do NOT create a duplicate card — one card covers all certs

[ ] node build-commands.js  -> builds clean (auto-runs validate)
[ ] node validate.js        -> 0 hard errors AND 0 command-lint literals (PASS)
[ ] node coverage.js --module NN -> unmatched list reviewed (carded or conscious skip)
[ ] completeness score reviewed; chains/notes filled where reasonable
[ ] placeholder audit reviewed; no un-canonicalized high-frequency tokens
[ ] PROGRESS.md updated — use the mandatory block-by-block log format from README.md
```

## Why this exists

The library was redone multiple times because the schema and conventions kept drifting, and
"is it done?" was answered by re-reading files. That is now mechanized: the contract is frozen
(`SCHEMA.md`), the vocabulary is centralized (`js/vars.js`), and correctness/completeness is a
command (`validate.js`). Follow this guide and modules don't need redoing - they either pass the
gate or the gate tells you exactly what's missing.
